## 2. Section 1 — OCR Baseline Reconciliation

### 2.1 Tracing the Exact Source of Discrepancy
In Milestone 3C.1, two separate OCR accuracy figures were reported:
1. **Verified Annotation Evaluation (`evaluate_verified_ocr.py`):** 18 / 50 exact matches (36.00%), 23.76% CER.
2. **Ablation Baseline (`ablation_ocr_preprocessing.py`):** 25 / 50 exact matches (50.00%), 20.72% CER.

Tracing the code execution paths revealed the precise source:
- **Historical Protocol 1 (Evaluated in `evaluate_verified_ocr.py`):**  
  Evaluated the static column `easyocr_predicted_text` stored in the CSV. This column was originally generated by [`PlateOCR.read()`](file:///d:/MZHR_FYP/INTELLIGATE/module2_vehicle/plate_ocr.py#L104-L140) via [`tools/generate_clean_ocr_crops.py`](file:///d:/MZHR_FYP/INTELLIGATE/tools/generate_clean_ocr_crops.py#L84). In `PlateOCR._make_variants()`, every crop was forcibly downscaled to a fixed height:
  ```python
  variants.append(preprocess_plate(plate_bgr, target_h=64))
  ```
  On high-resolution Pakistani license plate crops (e.g. $433\times 247$, $389\times 220$), resizing height down to 64 pixels blurred and destroyed the small 2-digit registration year codes (e.g. `12`, `14`, `16`). EasyOCR was unable to detect these downscaled small digits, yielding 18 exact matches.
- **Protocol 2 (Evaluated in `ablation_ocr_preprocessing.py`):**  
  `A_Baseline` passed the original, full-resolution raw crops directly into `easyocr.Reader.readtext()` without downscaling to 64px. Because high-resolution crops preserved their native character pixels, CRAFT text detection successfully detected both lines and small year digits, producing 25 exact matches.
- **Empirical Proof:**  
  Running fresh `PlateOCR(gpu=True, n_reads=3)` on the crops reproduced **17 / 50 exact matches (34.00%)**, matching the downscaled protocol within 1 read of voting variation, while running raw `easyocr.Reader` on native crops produced **25 / 50 exact matches (50.00%)**.

### 3.2 Multi-Line Strategy & Gate Safety Policy
1. **Selection:** **Variant D (Multi-Line Reading-Order Sort)** is the only strategy that produces a strictly monotonic improvement (+1 corrected, 0 degraded, CER reduced from 20.72% to 19.06%). It clusters bounding boxes into vertical lines by $y$-centroid proximity ($<0.45\times \text{height}$) and sorts left-to-right within each line.
2. **Experimental Designation:** Because the gain on this 50-sample development set is small (+1 sample), multi-line reordering remains **experimental**. It is not automatically enabled in the gate access `ALLOW` path without independent held-out testing.
3. **Gate Security Rule:** Automatic `ALLOW` continues to require strict exact registry matching with `confidence >= 0.85` from trusted internal perception. Incomplete reads (e.g. missing year digits) route to `REVIEW_REQUIRED`.

```

         │ (warmup: -7.94 ms)
         ▼
[Warmed Loop First Encounter (Case A)] ──► 22.39 ms (44.66 FPS, 20 iterations mean)

         ├── CPU Full 100-Frame Benchmark ──► 23.91 ms (41.83 FPS sustained)
         └── GPU Full 100-Frame Benchmark ──► 28.51 ms (35.07 FPS, +4.6 ms PCIe transfer)
```

1. **30.33 ms Isolated Post-Optimization Sum:**  
   The sum of 7 isolated subcomponent timers measured on a single, cold stranger frame immediately after process startup (`profile_face_runtime.py`). Includes initial PyTorch OpenMP thread-pool spawning and SQLite statement compilation.
2. **22.39 ms First-Encounter Reported Latency (Case A):**  
   The mean latency over 20 iterations of fresh stranger encounters in a warmed loop. JIT caches, memory buffers, and statement handles are warm, reducing latency from 30.33 ms to 22.39 ms (p50 = 21.39 ms).
3. **23.91 ms Full CPU Mean:**  
   Evaluated over 100 genuine test frames sampled from LFW. 98 frames had 1 face (mean ~23.5 ms), 1 frame had 0 faces (6.3 ms), and 1 frame had multiple faces (35.1 ms). The dataset-wide mean is **23.91 ms (41.83 FPS)**.
4. **28.51 ms Full GPU Mean (RTX 4060 Ti):**  
   On GPU, MiniFASNetV2 inference requires copying an $80\times 80\times 3$ float tensor across the PCIe Gen4 bus (`.to('cuda:0')`) and copying output logits back to host RAM (`.cpu()`). For a tiny 1.8 MB model at batch size 1, host-to-device transfer and CUDA stream synchronization add ~4.6 ms of latency. The CPU computes the forward pass directly in L1/L2 cache via AVX2 instructions with zero PCIe overhead.

## 5. Section 4 — SQLite Durability & Biometric Cache Safety

### 5.1 SQLite WAL Durability Tradeoff Analysis
In Milestone 3C.1, `EventStore._conn` was configured with:
```python
conn.execute('PRAGMA journal_mode=WAL')
conn.execute('PRAGMA synchronous=NORMAL')
conn.execute('PRAGMA busy_timeout=5000')
```
The durability and safety implications were formally audited and tested:

1. **Process Crash & Unhandled Exception Durability (100% Durable):**  
   In WAL mode with `synchronous=NORMAL`, commits write dirty pages into the OS filesystem page cache for the `-wal` file. If the Python process crashes, segfaults, or is terminated (`kill -9`), the operating system retains the dirty page cache and writes it to disk. Upon restart, SQLite reads the WAL header and replays all committed transactions. Tested and verified in [`test_sqlite_wal_transaction_durability_on_reopen`](file:///d:/MZHR_FYP/INTELLIGATE/tests/test_milestone3c_2_durability_and_cache.py#L32-L60).
2. **Sudden Power Loss Tradeoff:**  
   Unlike `synchronous=FULL` (which forces an OS `fsync` / `FlushFileBuffers` on every commit, costing 120–135 ms per write on Windows NTFS), `synchronous=NORMAL` syncs the WAL file to physical flash memory only during checkpoints. Therefore, in the event of an abrupt catastrophic power loss (power cable pulled):
   - Transactions committed in the final few hundred milliseconds before power cut may be lost (reverting to the state at the last sync).
   - **Database corruption does NOT occur:** SQLite's WAL framing format guarantees that un-synced or torn frames are ignored upon recovery, leaving the database completely valid and uncorrupted.
   - For an access-control system deployed on server hardware with an Uninterruptible Power Supply (UPS), `NORMAL` is the official recommended configuration by SQLite developers.
3. **Thread-Local Connection Cleanup:**  
   Implemented `store.close()` and `def __del__(self): self.close()`. Verified on Windows NTFS: all file locks are released cleanly without `WinError 32` (verified in [`test_thread_local_connection_cleanup`](file:///d:/MZHR_FYP/INTELLIGATE/tests/test_milestone3c_2_durability_and_cache.py#L100-L120)).

### 5.2 Biometric Cache & Encryption Safety
- **Gallery Invalidation:** Evaluated in [`test_gallery_cache_invalidation_lifecycle`](file:///d:/MZHR_FYP/INTELLIGATE/tests/test_milestone3c_2_durability_and_cache.py#L122-L170). The `gallery_revision` integer counter increments upon any enrollment or deletion. `FaceEngine.match()` compares its cached revision against the engine revision, immediately rebuilding its in-memory vector cache when modified.
- **Stranger-Cache Retention:** Active strangers are cached in RAM. Tested in [`test_stranger_cache_and_retention_pruning`](file:///d:/MZHR_FYP/INTELLIGATE/tests/test_milestone3c_2_durability_and_cache.py#L172-L215). Strangers older than 90 days are pruned from disk and RAM.

Raw 128-D float embeddings (512 bytes) never appear as plaintext on disk. All records in `cpu_faces` and `cpu_strangers` are 256-bit AES-GCM ciphertexts prefixed by a unique 12-byte cryptographic nonce.
